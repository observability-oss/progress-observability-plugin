# Connect an AI client to the Progress Observability MCP server

The server is **remote and read-only**: `https://mcp.observability.progress.com/mcp`.
There is no local process to install or start — this skill only writes the
client-side config that points an AI client at that endpoint and carries its
API key. Unlike a local MCP server, the key cannot be fetched or generated by
this skill: it exists only inside Progress Observability's own UI, so getting
one is a step the user performs, not one this skill automates.

This is the step every other skill in this plugin assumes is already done —
if you installed the Claude Code plugin or the Copilot CLI plugin, the
connection is wired for you already (see the repo README) and you don't need
this skill. It's for the `skills.sh` / single-skill-folder install paths, or
for wiring up a second client (Cursor, Codex) that the plugin install doesn't
cover.

## 1 · Prerequisites

Confirm both before writing any config:

- **A paid Progress Observability plan.** MCP access is not available on the
  Free plan — an authentication error mentioning the Free plan means this
  step was skipped, not that the config is wrong.
- **An MCP API key**, created in Progress Observability under **API Keys →
  MCP API Keys**. If the user doesn't have one yet, tell them to create it
  there with:
  - A name/description.
  - An expiration: `7`, `30`, `60`, or `90` days.
  - A scope: **Metadata only** (7 tools, no prompt/completion content) or
    **With content** (all 9 tools, including `*_with_content` detail calls).
    Ask which scope they need — content access requires acknowledging a
    prompt-injection risk warning in the UI before the key is created, so
    default to **Metadata only** unless they specifically need raw
    prompt/completion text.
  - The raw key is shown **once**. Tell the user to save it before leaving
    that page — there is no way to retrieve it again, only to revoke it and
    make a new one.

## 2 · Detect the client and its config file

| Client | Config file | Wrapper key |
|---|---|---|
| GitHub Copilot Chat (VS Code) | `.vscode/mcp.json` (project) or `~/Library/Application Support/Code/User/mcp.json` / `%APPDATA%\Code\User\mcp.json` (user) | `servers` |
| GitHub Copilot CLI | `~/.copilot/mcp-config.json` (user) or `.copilot/mcp-config.json` (project) | `mcpServers` |
| Claude Code | `.mcp.json` (project) or `~/.claude.json` (user) | `mcpServers` |
| Cursor | `.cursor/mcp.json` (project) or `~/.cursor/mcp.json` (user) | `mcpServers` |
| Codex CLI / ChatGPT Desktop / Codex IDE extension | `.codex/config.toml` (project) or `~/.codex/config.toml` (user) | `mcp_servers` (TOML table) |

**Default to project scope.** This plugin's own workflows are repo-scoped
(`health-check`, `trace-triage`, etc. run against the agent you're currently
in), and a project-scope file is safe to commit — it only ever holds a
reference to the key (Step 3), never the literal value. Use the user-scope
path instead only when the working directory isn't part of a repo, or the
user says they want the connection available across all their projects.
Don't ask about scope as a matter of course — decide from those signals, the
same way `fiddler-mcp-setup`'s agent detection resolves silently and only
surfaces a question when it's genuinely ambiguous.

If more than one client applies (e.g. VS Code open with a Copilot CLI terminal
inside it), ask which one the user means rather than guessing — each writes
to a different file.

**Once scope is decided, only touch that one file.** Don't also check or
grep the other scope's config "just in case" — for VS Code specifically, the
user-scope `mcp.json` lives outside the workspace, so reading it triggers an
unnecessary sandbox permission prompt for a file you were never going to
write to. Project scope means the project file only; user scope means the
user file only.

**Check for an existing entry first:** grep the target file for
`progress-observability` or `observability.progress.com`. If found, show the
user the current `url` and ask whether to leave it, update the scope, or
rotate the key — don't overwrite silently. If the file has other MCP
servers configured, add this entry alongside them; never replace the whole
file.

## 3 · Reference the key — never the literal value

**Never ask the user to paste the raw key into chat, and never write it as a
literal string in a project-scope config file.** A key typed into chat is
logged in the conversation; one hardcoded into a project file that gets
committed is a leaked credential. Use each client's own secret mechanism
instead:

- **GitHub Copilot Chat (VS Code)** supports an interactive secret prompt.
  Add an `inputs` entry and reference it — VS Code asks for the value once
  and stores it outside the repo, not in `.vscode/mcp.json` itself.
- **Claude Code, Cursor, GitHub Copilot CLI** interpolate environment
  variables in the header value. Have the user set
  `OBSERVABILITY_MCP_API_KEY` in their shell profile or a local `.env` that
  is already gitignored, then reference it — don't set it yourself or print
  its value.
- **Codex CLI** takes this a step further: `env_http_headers` maps a header
  name to an **environment variable name**, not the header value, so the raw
  key never appears in `config.toml` at all. Only use `http_headers` (the
  literal-value field) if the user explicitly wants the key hardcoded, and
  say plainly that doing so puts the raw key in a file that must then be
  kept out of version control.

## 4 · Write the config

Use the production endpoint in every case:
`https://mcp.observability.progress.com/mcp`. Fill in the file for the
detected client; don't touch the others.

**GitHub Copilot Chat** (`.vscode/mcp.json`, or the user-scope path from
Step 2 if that's the one that applies):

```json
{
  "servers": {
    "progress-observability": {
      "type": "http",
      "url": "https://mcp.observability.progress.com/mcp",
      "headers": {
        "X-Api-Key": "${input:observability-api-key}"
      }
    }
  },
  "inputs": [
    {
      "type": "promptString",
      "id": "observability-api-key",
      "description": "Progress Observability MCP API key",
      "password": true
    }
  ]
}
```

**GitHub Copilot CLI** (`~/.copilot/mcp-config.json`):

```json
{
  "mcpServers": {
    "progress-observability": {
      "type": "http",
      "url": "https://mcp.observability.progress.com/mcp",
      "headers": {
        "X-Api-Key": "${OBSERVABILITY_MCP_API_KEY}"
      }
    }
  }
}
```

**Claude Code** (`.mcp.json` or `~/.claude.json`):

```json
{
  "mcpServers": {
    "progress-observability": {
      "type": "http",
      "url": "https://mcp.observability.progress.com/mcp",
      "headers": {
        "X-Api-Key": "${OBSERVABILITY_MCP_API_KEY}"
      }
    }
  }
}
```

**Cursor** (`.cursor/mcp.json` or `~/.cursor/mcp.json`):

```json
{
  "mcpServers": {
    "progress-observability": {
      "url": "https://mcp.observability.progress.com/mcp",
      "headers": {
        "X-Api-Key": "${env:OBSERVABILITY_MCP_API_KEY}"
      }
    }
  }
}
```

**Codex CLI** (`.codex/config.toml` or `~/.codex/config.toml`):

```toml
[mcp_servers.progress-observability]
enabled = true
url = "https://mcp.observability.progress.com/mcp"
env_http_headers = { "X-Api-Key" = "OBSERVABILITY_MCP_API_KEY" }
```

`url` must stay a plain string — a markdown link in that field fails to
parse as TOML. Reserve `env_http_headers` for the key. If the client needs
an additional non-sensitive header (e.g. a `User-Agent` pin some Codex
versions require), add it under a separate `http_headers` table — never put
the API key there, since that field takes a literal value written straight
into the file.

Tell the user what activates the new entry, since it isn't the same for
every client and a plain reload is not enough on its own. Whenever you list
these activation steps — including in a final summary at the end of the
skill — any step that says to "enter" or "paste" the API key must also say
where to get it from: Progress Observability → **API Keys → MCP API Keys**
(the same place referenced in Step 1). Don't assume that page was already
mentioned earlier in the conversation; restate it inline so the step is
self-contained:

- **VS Code / Copilot Chat:** reload the window, but the `${input:...}`
  prompt for the API key only fires when the server actually **starts** —
  reloading alone does not trigger it. After reloading, open `.vscode/mcp.json`
  (or the user-scope file) and click **Start** on the `progress-observability`
  entry, or run *MCP: List Servers* → select it → **Start**. First start is
  what shows the key prompt; it won't appear again after VS Code stores it.
- **Copilot CLI, Claude Code, Codex:** these read the env var at process
  start, so a new session is enough — no interactive prompt to expect.
- **Cursor:** same as above — `${env:OBSERVABILITY_MCP_API_KEY}` is resolved
  from the shell environment on reload/restart, not via an interactive prompt.

This skill's job ends once the config is written and the user knows how to
activate it. Don't try to verify the connection here. Once it's active, the
next step is confirming the `progress-observability` tools actually work —
how depends on what's actually installed alongside this skill, so check
before assuming:
- If `/health-check` resolves as a command, run it.
- Otherwise, if a `health-check` skill is present (no command wired to it),
  tell the user plainly what to say instead: *"once it's connected, ask me
  to check your Progress Observability connection"* triggers it by
  description, command or no command.
- If `health-check` isn't installed at all, this skill has no diagnostic to
  hand off to — fall back to naming the tools that appear once the client
  picks up the new server, since that's the only self-contained confirmation
  available.
